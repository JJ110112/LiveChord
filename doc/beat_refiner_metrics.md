## What the numbers mean (for the HF model card)

The training corpus uses each song's own `beats[]` from the prior tracker (beat_this) as the supervision target whenever that output passed the gold/ok filters. So this F1 is:

- ✅ A measure of **how well the refiner preserves correct beats** while also pushing chord-boundary auxiliary signal into the same trunk.
- ✅ Monotonic in label quality (gold > ok > skip), which is the structural sanity check.
- ⚠️ **Not** a direct "refiner > beat_this" claim. That would require independently-annotated ground truth (e.g. MIREX Beatles, GTZAN_rhythm) which is on the v2 roadmap, not v1.

The most defensible single-number headline for HF: **0.920 beat F1 / 0.936 downbeat F1** at ±93 ms on the 510-song gold-quality holdout subset.

## Chord-boundary (cb) head — known weak

cb_f1 (gold) = 0.243. The cb head was added as auxiliary multi-task supervision to help the encoder trunk learn percussive vs harmonic transitions, not as a production prediction target. Chord-boundary events are an order of magnitude sparser than beats (~50-100 per song vs ~250-400 beats/song), and v1 used identical loss weighting across heads. v2 plan: separate cb-specific peak-picking thresholds + class-weighted BCE.

For HF release, do **not** advertise cb output as a primary capability — list it as "auxiliary multi-task signal, not production-ready" or omit from the headline.

## Reproduce

```bash
python scripts/eval_beat_refiner_holdout.py \
    --splits-dir backend/ai/splits \
    --features-cache G:/livechord/features \
    --checkpoint data/models/beat_refiner.pt \
    --out G:/livechord/eval_holdout_v1.json
```

The features-cache path can be substituted with any directory built by `train_refiner_1_extract.bat` (or its underlying `scripts/extract_features_batch.py`). Running on CPU works but is ~10× slower; expect ~30 min on a recent laptop CPU vs 3 min on a desktop GPU.
